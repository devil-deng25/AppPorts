# 意外断开外置盘的影响

迁移后的数据仍然依赖外置盘。两轮拔盘实验中，原生 APFS 卷也出现过数据库损坏；磁盘映像在重新接入后无法挂载。结果说明需要正常弹出与备份，不能给出“最多丢几条记录”的保证。

## 实验条件 {#environment}

实验于 2026 年 9 月 19 日进行，系统为 macOS 27.0（26A428），使用一块 64 GB USB 存储。比较直接使用原生 APFS 卷，与同一设备上承载 APFS 的 sparsebundle 磁盘映像。

测试数据包括连续写入的 SQLite 数据库（WAL 模式、同步级别 FULL）和普通文件。第二轮额外启用更强的写入同步请求。两轮都在持续写入时直接断开设备，属于破坏性测试。

## 怎样验证 {#method}

1. 建立测试数据库与文件，持续写入并记录最近已提交的序号。
2. 写入过程中拔出设备，再重新连接。
3. 检查卷或映像能否挂载、文件是否存在、数据库完整性和可恢复记录。
4. 改变同步设置后重复一轮，保留无法挂载和恢复失败的结果。

## 观察结果 {#results}

| 轮次与目标 | 拔盘前最后提交序号 | 重新接入后的结果 |
| --- | --- | --- |
| 第一轮：原生 APFS | 7177 | 数据库报告损坏；恢复工具取回 7172 行，50 个测试文件仍在。 |
| 第一轮：sparsebundle | 25574 | 映像无法挂载，未能正常检查内部数据库。 |
| 第二轮：原生 APFS，额外强同步 | 1906 | 恢复后有 1905 行，数据库完整性检查通过。 |
| 第二轮：sparsebundle，额外强同步 | 373 | 映像仍无法挂载。 |
| ASIF 磁盘映像尝试 | 未进入有效拔盘测试 | 实验中止，不能记作通过或失败。 |

“完整性检查通过”只说明该数据库结构可读，不代表所有最近提交都已保留。无法挂载也不等于已经证明任何恢复工具都无法取回数据。

## 对使用有什么意义 {#meaning}

退出使用外盘的应用、等待保存完成，再通过系统正常弹出设备。数据库、虚拟机和聊天记录等持续写入内容尤其需要注意。AppPorts 的迁移与复制检查不能防止设备突然断电。

备份应覆盖实际存放数据的外置盘。应用本体在本机，也可能正在读写外部的数据目录。

## 结论的范围 {#limits}

这是单一设备上的两轮样本，不能估计故障概率、最大损失量，也不能证明某种格式永不损坏。两组的写入速度不同，速度本身不足以证明数据已经持久保存。实验没有验证所有磁盘映像格式、设备控制器或系统版本。
