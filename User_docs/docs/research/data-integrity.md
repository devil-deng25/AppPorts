# 数据完整性：文件复制完就够了吗

“复制成功”至少需要回答三件事：内容是否一致、必要属性是否保留、复制期间源数据有没有变化。历史实验中，旧复制流程曾报告成功，但目标数据库缺少源端后来提交的记录。

## 实验条件 {#environment}

实验于 2026 年 10 月 1 日进行，系统为 macOS 27.0（26A428）、Swift 6.4、arm64。样本均为合成测试数据，不涉及实际使用中的个人资料。

属性与后台写入测试使用当时的旧复制代码；另一次迁移与还原测试使用 4 GiB、未加密的 APFS 磁盘映像。它们不是拔出真实外置设备的测试，也不是当前版本的重新复验。

## 怎样验证 {#method}

1. 建立含普通文件、权限属性与硬链接关系的目录，复制后逐项比较。
2. 建立两个静态对照和四个受控写入场景，让独立进程在复制后段修改源数据。
3. 对 SQLite 数据库检查记录数和完整性，区分“结构损坏”与“遗漏已提交记录”。
4. 在隔离 APFS 映像上调用旧迁移与还原流程，检查完整往返结果。

## 观察结果 {#results}

| 场景 | 结果 |
| --- | --- |
| 同卷属性复制 | 普通文件内容校验相同，但目录访问控制、文件标志、硬链接关系及部分组属性没有完整保留。 |
| 两个静态写入对照 | 源与目标一致。 |
| 四个强制安排的后段写入 | 旧流程没有发现源数据在复制期间改变。 |
| SQLite WAL 后段提交 | 源数据库有 3 行，目标只有 1 行；两边完整性检查均通过。 |
| APFS 映像：静态文件与关闭的 100 行数据库 | 旧迁移、还原往返后内容一致。 |
| APFS 映像：文件由 19 字节增至 48 字节并同步 | 旧流程报告成功并清理原备份，挂载与还原结果仍只有 19 字节。 |

数据库少两行，说明较晚提交的记录没有被复制，但数据库结构仍可读取。这是人为安排写入时机得到的结果，能证明问题可能发生，无法据此估算发生概率。

## 当前做法与使用建议 {#current}

当前复制流程会核对源与目标，并在进度完成后再次检查；迁移还会在切换或删除前复查，以便发现变化时停下并保留恢复材料。文件系统属性的处理也比旧流程更严格。

这些检查不等于能冻结任意后台写入者。因此操作前仍需保存并完全退出相关应用、下载、构建或同步任务。检查通过也不能替代独立备份。

## 结论的范围 {#limits}

同卷测试没有证明所有外部文件系统都能保留任意所有者或系统属性。磁盘映像测试直接调用迁移程序，没有覆盖真实应用的完整界面操作。旧缺陷已用于改进当前流程，本页不据此断言当前版本仍会产生同样结果。
