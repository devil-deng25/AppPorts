# 重启与外置盘自动接回

自动接回的目标，是让外部数据卷尽早回到原目录。实验表明，用户登录、磁盘上线、系统授权和实际挂载位置都会影响完成时间；后台任务启动了，不代表数据已经可用。

## 实验条件 {#environment}

实验于 2026 年 9 月 22–23 日进行，系统为 macOS 27.0（26A428）、Apple Silicon，FileVault 开启。外部存储为未加密 APFS，使用两个微信相关数据卷。AppPorts 已获完全磁盘访问，全程没有重签应用。

验证包括受控后台进程探测、真实重启时序，以及临时卷的重新挂载检查。它们是不同层面的测试，不等同于每次都重新迁移完整数据。

## 怎样验证 {#method}

1. 比较系统级后台进程和已授权的用户进程能否访问容器路径。
2. 重启并记录用户登录、应用启动、接回任务启动、数据卷就位的相对时间。
3. 调整任务启动配置，再次重启比较，检查是否出现反复空跑。
4. 用临时卷检查系统先挂到其他位置、磁盘延迟出现时的处理，逐次核对实际挂载位置。

## 观察结果 {#results}

| 检查项 | 观察 |
| --- | --- |
| FileVault 解锁前 | 受测环境中的用户数据路径尚不可用，无法提前挂到该路径。 |
| 系统级进程直接挂载 | 即使以管理员身份运行，仍受容器访问授权限制。 |
| 启动已授权的用户任务 | 用户会话存在后可行；会话尚未建立时失败。 |
| 启动配置调整前的一次重启 | 登录约 24.7 秒后启动任务，约 37 秒后两个卷就位。 |
| 调整后的一次重启 | 约 4.6 秒后启动任务，约 18 秒后就位；应用仍可能更早启动。 |
| 系统已将卷挂到其他位置 | 挂载命令可以返回成功，却没有把卷移到指定目录。 |
| 延迟上线与重挂检查 | 等待卷变化后重试、检查位置并按需重挂，有助于完成接回。 |

这些秒数来自具体重启样本，不是性能承诺。后续一次重启仍出现应用先于数据就位的情况，不能把启动更早写成问题完全消失。

## 对当前使用有什么意义 {#meaning}

AppPorts 会核对实际挂载位置，并在登录或卷变化后尝试接回。外置盘晚接入、系统繁忙、需要解锁或管理员授权时，仍可能需要等待或打开 AppPorts。

建议先连接外盘，检查“已挂载”，再打开依赖这些数据的应用。移动或更新 AppPorts 后打开一次，以便检查后台任务的程序位置。

## 结论的范围 {#limits}

实验未证明能在所有登录应用前完成，也未覆盖所有 FileVault 状态、系统版本和硬件。临时卷的快速重挂结果不能替代真实重启验证。曾测试的系统守护进程与挂载配置保存在[历史方案归档](/docs/archive/mount-experiments)。
