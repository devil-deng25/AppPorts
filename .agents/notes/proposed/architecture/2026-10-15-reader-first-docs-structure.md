# Agent Note: 面向普通用户的文档目录与内容深度

Status: proposed

## Problem

当前中文站有 31 篇正文，侧栏把操作、底层机制和故障诊断并列展示。数据迁移分散在基础实现、工具识别、挂载、签名和容器身份等页面；FAQ、故障排除、日志页又重复部分说明。普通用户为完成一次迁移，需要先判断该看哪一种技术文档。

正文深度也不均衡：挂载迁移约 7,600 字符，开机挂载实验约 17,900 字符，包含大量命令、日志和调查时序。旧说明还有版本偏差：应用策略仍把旧 Contents 方案作为主要选项；设置页仍描述迁移后自动重签；徽章页缺少现有界面的“签名待检查”。拔盘报告将两轮样本概括成固定损失范围，挂载报告把系统检查概括成只比较路径字符串，均需收窄。

读者需要先知道能做什么、如何操作、遇到问题怎么办；感兴趣时再读原理和实验。术语需要一个稳定入口，赞助者也需要明确的信息修改联系方式。

## Proposal

本提案只规划简体中文的目录、页面职责、写作深度、证据处理和迁移方式。当前交付为待审批方案；批准前不重写、移动或删除文章，不修改导航、首页、赞助页面或本地预览。

产品哲学与五篇操作文章直接作为顶层页面，不设置“使用指南”一级标题。“原理”“实验记录”“帮助与支持”保留为分组，目录最多两层。“设置与权限”“更新日志”“赞助”各自独立为顶层页面，词汇表放在主目录最后。词汇表页面内可以分组，不继续嵌套目录。

正文按普通用户的任务组织。操作指南能够独立完成任务，链接用于补充解释，不能把必要步骤、权限或风险藏到链接之后。技术细节的精简不改变产品的真实限制。

### 页面职责与深度

下列字数是中文正文的编辑目标，表格和必要插图可另计，不能为了达标删掉关键前提。

| 页面类型 | 建议深度 | 必须回答 | 收起或移走的内容 |
| --- | --- | --- | --- |
| AppPorts 的产品哲学 | 约 300–600 字 | 为什么做 AppPorts；希望提供怎样的使用体验；设计原则如何影响取舍 | 具体操作步骤、底层实现和逐项功能清单 |
| 快速开始 | 约 500–800 字，3–5 分钟 | AppPorts 做什么；需要什么；下载、授权和首次成功迁移；结果怎么看 | 迁移算法、完整策略目录；产品哲学链接到独立文章 |
| 操作指南 | 每页约 500–1,000 字 | 适用情况 → 准备 → 步骤 → 成功表现 → 遇到问题 | 源码符号、检测规则、底层命令和实验推导 |
| 原理 | 每页约 600–1,200 字 | 用途、发生的变化、方式差异、对用户的影响、适用限制 | 大段代码、文件格式、内部状态机、逐行系统日志 |
| 实验记录 | 每页约 600–1,200 字及结果表 | 研究问题、环境、过程、观察结果、能说明什么、不能说明什么 | 调查聊天、追问过程、逐轮探索日记、完整原始日志 |
| 徽章与状态 | 按需查表 | 看到什么、代表什么、是否需要处理、能点什么、下一步 | SF Symbols 名、内部枚举值、判断算法 |
| 常见问题与排查 | 单问题约 80–200 字 | 症状、优先检查、可执行下一步、何时反馈 | 同一操作的完整重复教程、大段诊断日志 |
| 词汇表 | 每词 1–3 句，加链接 | 白话定义、一个例子、与相近词的区别 | 另一套完整原理文章 |

页面正文通常使用二级标题，确有必要时用三级标题；不使用四级及更深标题。代码和日志不因折叠就可以无限保留。用户无须执行终端命令即可走通主操作流程。

更新日志保持按版本查阅；隐私政策、许可证不套用短文限额，不在本次精简中删除必要条款。贡献者指南面向开发者，保留测试和开发细节。

### 产品哲学与操作页面

保留现有“透明体验、策略稳定、低系统负担、广泛国际化、无障碍友好”五项产品哲学及其原意。文章说明这些原则如何影响 AppPorts 的选择，不以精简技术内容为由删除产品理念。涉及当前实现的表述仍需校准，例如“低系统负担”不能继续写成与现有登录代理冲突的“不依赖守护进程”绝对承诺。快速开始只链接此页，不要求先读产品哲学才能操作。

| 页面 | 主要内容 |
| --- | --- |
| AppPorts 的产品哲学 | 沿用 `AppPorts.md`，保留产品简介与五项哲学，技术策略移至原理；作为目录第一篇独立文章 |
| 快速开始 | 用一句简介引入安装引导；给出应用迁移、数据迁移两个入口，首次操作只选一条完成；下载继续使用已指定地址 |
| 迁移应用 | 迁出应用、查看结果、应用更新后的处理；App Store 差异只保留会影响用户操作的部分 |
| 迁移数据 | 应用数据、工具目录、自选文件夹三种入口；按界面实际提供的操作进行，不要求用户先读系统容器知识；只列常见工具例子 |
| 还原、接回与解除链接 | 先用对照表区分三种操作，再给应用和数据对应步骤；说明真实数据在哪里、哪些操作只是移除入口 |
| 外置盘与日常使用 | 格式与权限要求、连接和正常弹出、换盘、空间、启动时机；APFS 的强制条件只写在真正要求它的操作上 |

### 原理的五篇文章

| 页面 | 必须讲清 | 范围边界 |
| --- | --- | --- |
| 应用迁移方式 | 真正应用与本地入口分别在哪里；启动入口、文件夹镜像和链接的作用；更新保护为什么存在 | 按拟发布版本核对默认方式。旧 Contents 方案只作为历史兼容说明；默认关闭的透明混合原型不列为普通用户可选推荐方案 |
| 数据迁移方式 | 普通目录链接与容器挂载的区别；为什么应用本体和数据需要分开；为什么某些操作要求 APFS | 不写成“所有迁移都必须 APFS”或“只要挂载成功应用就一定能读写”；系统容器与 APFS 容器明确区分 |
| 徽章与状态 | 应用位置和链接、更新保护、应用类型、签名状态、数据目录状态；常见组合如何理解 | 对照实际渲染的所有用户可见徽章，包括“签名待检查”，不把内部“卷丢失”当成界面“外置盘未连接”的文字；颜色不能是唯一判断依据 |
| 经典模式 | 它是什么、为何保留、开启后改变哪些操作、适合谁、为何默认关闭、如何转回推荐方式 | 关闭开关不等于自动还原旧数据；不能把经典模式等同于所有数据迁移。是否允许重签、如何确认，以版本实际行为为准，不能沿用已移除的自动重签描述 |
| macOS 27 与迁移方式的变化 | 在已测试系统中，旧容器访问方式、应用签名和授权为什么可能影响启动与读写；AppPorts 为何调整做法 | 不宣称所有应用都会失败，不把签名错误直接解释成数据损坏；系统机制只解释到影响用户判断的程度 |

“macOS 27 升级与修复”仍独立承担操作入口，开头先用一段白话回答：哪些旧迁移用户需要更新 AppPorts、检查现有迁移，以及为什么更新后还可能需要修复。这里的“需要升级”明确区分更新 AppPorts、升级 macOS、调整旧迁移方式三个动作，不能写成要求所有用户升级 macOS 27。

该操作页按“尚未升级系统 / 已升级且异常 / 检查正常”分流，并链接原理说明。更新 AppPorts 本身不等于恢复已改变的应用签名。原理页不重复完整修复步骤，操作页也不复制系统机制长文。

### 实验记录的编排

每篇只交付整理后的实验报告，顺序固定为：

1. 要回答的问题，以及一句有条件的结论。
2. 必要环境：实验日期、系统与构建、应用版本、存储类型、签名和授权条件。
3. 实验过程：对照组、改变了什么、如何观察和核对，通常 3–6 步；保留失败和中止项。
4. 结果表：启动、读写、恢复或完整性等实际观察，不把“命令返回成功”当成所有结果。
5. 对使用的意义、适用范围和未验证部分。
6. 相关原理与操作入口。

| 拟定主题 | 已有依据 | 要保留的重点 |
| --- | --- | --- |
| 符号链接为什么不总是可用 | `research/sandbox-symlink.md` | 原位置、容器内与容器外目标的对照；官方签名和被重签样本分开；限制结论到受测应用、授权和系统，不能推成所有软链接都不能用 |
| 挂载迁移与系统授权 | `research/sandbox-mountpoint.md`，容器结构及权限相关笔记 | 挂载者具备权限与目标应用具备访问权限是两件事；第三方应用和系统应用的观察差异；更正“只比较路径字符串就能绕过所有检查”的概括 |
| 意外断开外置盘的影响 | `research/unplug-test.md`，APFS 预检与验证证据笔记 | 第一轮原生卷数据库也出现损坏并经恢复取回部分记录；第二轮与磁盘映像结果分别列出；ASIF 中止不计为通过或失败。两轮样本不能变成故障概率、固定丢失量或“APFS 永不丢数据” |
| 重启与外置盘自动接回 | `research/prelogin-mount.md`，卷事件重试笔记 | 登录、解锁、授权与实际挂载位置的关系；保留关键对照结果，去掉逐次重启流水；不能承诺永远在应用启动前接回 |
| 为什么有些容器目录不能搬（新增整理） | 企业微信容器完整性笔记及其原始验证材料 | 系统结构目录与业务数据目录的差别；真实启动验证和系统函数探针分开；部分组合通过不等于所有应用的任意子目录都可迁移 |
| 数据完整性：文件复制完就够了吗（新增整理） | 严格复制、APFS 验证证据笔记及其原始材料 | 正文内容、文件属性和仍在写入的数据分别核对；旧构建的数据库仍可读但缺少后续记录这一反例；旧故障不作为当前版本仍存在的断言 |

原生卷、隔离磁盘映像、模拟测试、真实应用验证分别注明。历史实验仍用历史版本，不因文章重写变成对最新构建的复验；速度不同不能单独证明某一轮数据是否落盘。首期新增两篇只整理既有实验，不执行新的拔盘、重启、真实应用迁移或系统权限修改。

后续可扩展“迁移中断后的继续处理”“迁移与还原性能对照”等主题，但只有来源中的环境、过程和结果足够完整时才独立成文。不把源码推断、开发提案或单测通过包装成已经做过的真实实验。

### 实验材料的公开边界

- 不发布任何聊天记录、对话引用、提示词、提问者、回答者、任务名称或调查过程中的私人叙述。
- 去除真实用户名、账户 ID、私人文件名、个人卷名、序列号、令牌、交易信息，以及含这些信息的截图、日志和图片元数据。路径使用 `<用户>`、`<测试盘>`、`<测试账户>`；同一对象的替代名保持一致。
- 为解释结果所必需的公开应用名、系统版本、测试日期和汇总计数可以保留。原实验使用真实应用还是合成数据必须如实说明，不能为了脱敏把它改称另一种实验。
- 公开页不直接引用内部决策笔记、私有归档路径或完整证据包。内部保留逐项来源对应，公开页仅给经过检查的简短证据摘要和可公开的来源。
- 隐私清理不能删除失败、数据损坏、未测试项和不利结果。证据缺失时标记范围不足，不补写实验。

### 词汇表范围

词汇表放在主目录最后，先解释 AppPorts 自有说法或在本产品中有特定含义的操作，给每个词固定锚点。旧称和英文别名用于搜索，不在正文反复堆叠。

| 分组 | 首批词条 |
| --- | --- |
| 应用的位置与入口 | 本地入口／启动壳／壳门（Stub Portal）、真实应用／外部副本、文件夹镜像（Folder Mirror） |
| 迁移与恢复操作 | 应用迁移、数据迁移、链接迁移、挂载迁移、迁回／还原、接回、解除链接、整理 |
| AppPorts 模式与保护 | 经典数据迁移模式、锁定迁移／更新保护、待迁出 |
| 必要背景词（明确并非 AppPorts 独创） | 符号链接、沙盒、应用容器／容器数据、APFS 容器与卷、挂载点、开发者签名、重签名、恢复原始签名 |

词条只给白话定义、简短例子和原理链接；状态如何处理统一引用“徽章与状态”。明确“接回”不等于把数据搬回内置盘、“解除链接”不等于删除外部真实副本、“恢复原始签名”不等于再次重签。具体按钮及结果仍按目标版本核对。

### 页面之间如何引用

每个概念只指定一个主要解释页面，其他页面在首次出现时给一句必要说明和描述性链接。操作页通常附 2–4 个“相关内容”，但不为凑链接数量添加无关入口，不做“一句话一跳”。链接可直达相关小节。

| 阅读位置 | 主要去向 |
| --- | --- |
| 迁移数据中出现“挂载迁移” | 词汇表定义 → 数据迁移方式 → 挂载与授权实验 |
| 看到“签名已替换” | 徽章与状态 → macOS 27 升级与修复；需要原因时再读原理 |
| 在设置看到“经典模式” | 词汇表简释 → 经典模式 → 迁移数据或旧方式修复步骤 |
| 关心外置盘断开 | 外置盘与日常使用 → 意外断开实验；异常现象再转问题排查 |
| 实验报告结束 | 回到对应原理和推荐操作，不要求用户照搬实验命令 |

## Alternatives considered

- 只把现有技术页移到“原理”：迁移成本最低且保留全部材料，但不能解决操作与原理混写、版本错误、术语重复和实验叙事过长，因此不足以满足本次目标。
- 把所有技术内容压成一篇原理长文：顶层入口最少，但应用迁移、数据迁移、徽章和经典模式的阅读任务不同，会重新形成难检索的长文；采用一个一级组和五篇短文章。
- 操作和实验全部混排在同一组：相关内容看似集中，但普通用户难区分建议操作、历史实验和验证局限；使用独立实验组并通过链接关联。
- 一次重写八种语言并重命名全部路径：结构最一致，但会扩大翻译、链接兼容和主分支协作范围；本次中文先行，稳定 URL 尽量沿用，译文切换保留线上方式。

## Risks

精简可能丢失必要限制，所以权限、外盘依赖、旧数据处理和失败结果必须保留。跨页引用会增加维护工作，依靠固定锚点、单一解释来源和链接检查控制。

原始实验材料可能缺少版本或完整过程，两篇新实验在证据核对前只能算选题，不承诺补成已经验证的结果。历史结论与当前实现可能不同，必须同时写清实验时间和今日适用范围。

签名和备份仍有并行改动，正式成稿必须以指定版本再核对，不能现在把工作副本当成发布承诺。其他语言暂时保留旧结构，跳转后的目录及外观会不同，这是中文先行方案的已知代价。
