# Agent Note: 写入登记按进程身份清理，挂载代理改用挂载事件触发

Status: implemented

## Problem

2026-10-23 的 Excel/Outlook 迁移在 10 月 23 日当天失败 168 次，报「仍有无法确认写入兼容性的 AppPorts 进程（PID 46013…）」。核查结论是三件事叠在一起：

1. PID 46013 是 10-20 启动的旧镜像（能力串 `appports-verified-writer-v5`），磁盘上的可执行文件在 10-23 08:07 被替换成 v6，另一个实例从 `AppTranslocation` 里跑着同样的包。登记文件里留着旧镜像的身份，`WriterAdmission` 判定「无法确认兼容性」是正确的，但错误文案只说「仍有进程」，用户无法判断该杀谁。
2. `.writer-presence/` 从不清理：5 天内累积 20 155 个登记文件（79 MB），日志 33 MB/天。
3. 同一时段挂载代理被 launchd 拉起 21 919 次。代理 plist 用 `WatchPaths: ["/Volumes"]`，代理无事可做时以非零码退出，而 `KeepAlive {SuccessfulExit: false}` 又要求重启，撞上 10 秒节流后形成稳定循环。用 CoreServices 的 FSEvents 探针实测 `/Volumes` 在迁移后的 Chrome 数据目录上有 0.7 事件/秒的持续读写，`WatchPaths` 因此永远处于「刚变化」状态。

## Decision

`WriterAdmission.registerCurrentProcess()` 在写入自己那条登记后，顺带清理失效登记：进程已退出，或进程仍在但内核身份（pid + 启动时间 + 可执行路径）与登记不一致，都视为失效。清理只在登记数超过 64 时启动，单次最多处理 512 个，避免每次登记都全目录扫描。`.incompatibleWriter` 的错误描述追加一段可执行提示：该实例的启动时间、磁盘上的镜像在此之后被替换、以及「菜单栏退出或 `kill <pid>` 后重试」。

`ContainerMountAgentInstaller` 的 plist 从 `WatchPaths: ["/Volumes"]` 改成 `StartOnMount: true`。挂载事件才是代理需要醒来的理由，`/Volumes` 的内容变化不是。

`AdministratorAuthorization.reuseInterval` 从 120 秒改为 300 秒，与 AuthServices 对 `system.privilege.admin` 的空闲时限对齐。改长不会延长系统侧的授权，只是不再在授权仍有效时先丢掉脚本、让同一批迁移中途多弹一次密码框。

## Related decisions

- 与[root 所有的应用只授权位置交换和已验证旧副本清理](2026-10-20-root应用迁移授权.md)部分重叠：本篇只调整授权会话的复用窗口，不改变该篇定义的授权边界与一次性入口。
- 与[容器卷改为挂载事件驱动](2026-09-23-event-driven-container-remount.md)部分重叠：保留事件驱动重挂，只把登录时的触发方式从目录监视换成挂载事件。
- 与[后台写入者身份](2026-10-13-background-writer-identity.md)部分重叠：那篇定义的内核身份判定（pid + 启动时间 + 可执行路径）不变，本篇只增加「失效登记可以删」这一条收尾动作。

## Alternatives considered

- **登记失败时清空整个 `.writer-presence/` 目录**：能立刻解除阻塞，但会把正在运行的其他实例登记一起删掉，admission 反过来放行并发的写者，破坏它存在的理由。
- **只调大 launchd 的 `ThrottleInterval`**：重启频率下降，无效启动依旧发生，日志和登记仍按天增长，根因没动。
- **让代理无论如何都 `exit 0`**：`KeepAlive {SuccessfulExit: false}` 不再重启，循环停止，但真正需要重挂时代理崩溃也不会被拉起，代价比换触发方式大。
- **在 `WatchPaths` 里换成外部盘的具体卷路径**：仍是目录内容监视，`/Volumes` 之外的挂载点（新插的盘、网络卷）会漏掉，且初始挂载不一定产生目录事件。

## Consequences

旧镜像登记会在下一次登记时被自动收尾，用户不必再手工找 PID；错误文案给出了可执行的退出方式。代理只在真正发生挂载时启动，登录时的那次重启循环消失，`/Volumes` 的读写噪声不再转化为进程活动。登记目录会在长时间运行后保持在有界规模内。

代价是：清理依赖 `proc_pidinfo` 一类的内核身份读取，读取失败时按「不可判定」保留登记，宁可留垃圾也不误删活着的实例；`StartOnMount` 的登录竞态（登录瞬间已有挂载、代理是否需要补一次全量重挂）需要在真机上复验，代码注释里已标明这一条。

## Verification

本次改动在无 Xcode 的机器上完成，只做到服务层 `swiftc -typecheck`（97 个非视图文件 + 4 个新增特权助手文件，除视图文件缺失导致的 `DiagnosticExportDialog` 外无错误）。没有执行 `xcodebuild clean build`，也没有运行 `AppPortsTests`，因为本机只有 Command Line Tools 且 `security find-identity` 报告 0 个有效身份。代理触发方式的真机验证（登录、插拔盘、迁移后重挂）仍需在装有 Xcode 的环境补做。
