# Agent Note: Finder 原生整盘弹出与分散挂载基线

Status: implemented

## Problem

挂载迁移的数据卷位于外盘 APFS 容器内，但挂载入口位于原数据目录。需要先确认 Finder 是否已经能够联动弹出这些卷，再判断是否需要改挂载位置或增加弹出协调服务。目录嵌套、单卷卸载、整盘弹出和 AppPorts 自动重挂不能混为同一种行为。

## Decision

本轮以真实 USB 的 Finder 操作、独立 APFS 映像的命令行对照和系统卷事件作为基线，只记录调查结果，不实现新的弹出策略。

USB 实验仅操作用户明确授权的 64 GB 爱国者 U352：物理容量 62,914,560,000 字节，APFS 容器 UUID `B74D25AF-A762-4B93-A957-AD050EFCC83C`，原卷 APTEST UUID `EBDC9D56-CE50-4DB8-9013-A41D182DBC11`。不格式化原卷，不操作另一块承载真实数据的外置 SSD。

在此容器新建两个自有测试卷，挂到独立临时目录，使用 `nobrowse`、`noowners`，每卷写一个哨兵文件。测试卷 UUID 分别是 `9C35A76E-DB4B-47D6-BC7A-27C2FA6A057C` 和 `854F185A-88AE-4B0B-86C6-4F72F80DC9AB`。设备号在重新连接后变化，后续操作始终重新解析 UUID 和容器归属。

事件观察器使用 Disk Arbitration，审批回调只记录并返回允许，既不拒绝也不发起任何挂载或弹出。命令结果、实际挂载表、卷 UUID 和介质消失共同证明结果，不以 Finder 图标消失单独判定成功。

## Verification

环境：2026-10-23，macOS 27.0.1（26A434），Apple Silicon。已安装的 AppPorts 显示版本 2.0.0，主程序和原有登录代理保持启用。本轮没有替换构建；版本号不足以证明安装产物等同当前源码。

| 场景 | 实际操作 | 观察结果 |
| --- | --- | --- |
| USB 侧边栏，无占用 | 点击 APTEST 右侧推出按钮 | 两个隐藏数据卷先卸载，APTEST 随后卸载，APFS 容器和物理 USB 最后消失；没有额外确认框 |
| USB 桌面，数据卷被占用 | 在桌面选中 APTEST 后按 Command-E；独立 Python 进程保持数据卷哨兵文件打开 | 空闲数据卷先卸载，被占用数据卷未卸载，APTEST 仍挂载；系统提示 APUSBData 被使用，继而提供重试、取消和强制推出；选择取消 |
| USB 桌面，释放占用 | 退出测试占用进程，恢复空闲数据卷，重新从桌面按 Command-E | 三个卷依次卸载，容器和物理 USB 消失；没有使用强制卸载 |
| 映像，分散挂载 | 只对主卷执行 `diskutil unmount <主卷UUID>` | 主卷卸载，两个挂在其他目录的数据卷仍挂载 |
| 映像，嵌套挂载 | 把数据卷挂在主卷的两个子目录，再仅卸载主卷 | 父卷卸载失败，三个卷仍挂载；没有自动级联卸载 |
| 映像，嵌套挂载后整盘弹出 | 对自建映像的整盘执行 `diskutil eject` | 三个卷均卸载，映像整盘离线 |

侧边栏事件序列以第一个数据卷卸载审批为 0 秒：另一个数据卷在 +0.081 秒、主卷在 +0.222 秒收到卸载审批；容器在 +0.525 秒、物理盘在 +0.674 秒收到弹出审批；物理盘在 +0.755 秒消失。桌面成功轮也观察到相同的先卸卷、后弹盘顺序。这些是本轮事件间隔，不是性能承诺。

AppPorts 登录代理的 launchctl 运行次数随本轮卷变化增加，说明监听确实被唤醒。桌面成功弹出后，连续 30 秒、每 5 秒查询测试卷 UUID 均无法解析；不能据此宣称已证明所有自动重挂竞态安全。

最后一次重新插入后，按 UUID 和原 APFS 容器重新核对两个测试卷，哨兵内容与写入时一致。仅删除这两个自建卷；复查容器只剩原来的 APTEST，其 UUID 不变且正常挂载。自建映像已正常弹出并删除映像文件，观察器和占用进程已退出。Finder“在桌面显示外置磁盘”已恢复为原来的关闭状态，测试时最小化的原有 Finder 窗口已恢复。生产记录库没有由本轮脚本写入。

仅新增本篇调查笔记，产品代码无改动，因此没有运行产品构建或回归套件。笔记树、格式与归档校验均通过。

### Evidence limits

- 测试卷复现的是挂载位置和参数，没有加入生产 ContainerMountStore，没有迁移真实应用数据。挂载点位于 `/private/tmp`，不是受 TCC 保护的真实应用容器。因此本轮不覆盖真实受管记录、沙盒应用运行、后台恢复任务与弹出之间的竞态。
- 审批观察器参与系统仲裁但始终放行；未做移除观察器后的重复 USB 对照，不能将上述亚秒间隔解释为无观察器时序保证。
- 没有关闭 AppPorts 的独立对照，没有测试加密卷、其他 APFS 容器、多分区外盘、最低 macOS、Intel 或物理强拔。正常弹出结果不证明断电安全。
- 原始本机证据位于 `/tmp/AppPorts-eject-20261023-01/`：事件 JSONL、场景快照、命令记录、临时 Swift 观察器和 Python 夹具。快照包含本机挂载表，不提交原始内容；临时路径不是长期证据存储。

## Alternatives considered

- **先把数据卷挂到主卷下面**：目录关系直观，而且整盘弹出时能够一起离线；但普通父卷卸载实测失败，目录嵌套没有提供单卷级联能力，还改变原数据入口，因此不能用它替代弹出机制验证。
- **直接增加常驻协调服务**：可以管理主动弹出和重挂抑制，但会引入请求识别、跨进程状态和失败后的部分卸载恢复；本轮已经观察到 Finder 原生联动，尚无证据支持先承担这些复杂性。
- **只用磁盘映像验证**：重复连接方便，适合区分单卷与整盘语义；但不能替代真实 USB 的 Finder 操作，因此两类证据分别报告。

## Consequences

当前系统和这块 U 盘上，数据卷分散挂载、使用 nobrowse 不妨碍 Finder 原生整盘弹出。后续讨论可以保留原挂载结构，以具体失败与自动重挂竞态为调查对象，不能仅因挂载目录不相邻就认定需要新服务。

占用失败可能留下部分卷已卸载的状态，因此任何后续弹出协调设计都必须重新盘点现场，不能假定整盘操作具备原子性。测试的代价是需要实物反复拔插、短暂修改并恢复桌面显示设置；受管记录与代理恢复的真实联动仍是明确缺口。本轮不修改产品代码，也不把未执行的集成场景算作通过。
