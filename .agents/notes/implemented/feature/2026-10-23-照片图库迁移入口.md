# Agent Note: 「目录迁移」页新增照片图库卡片

Status: implemented

## Problem

照片图库通常占几十 GB，是本地盘上最值得搬到外置盘的一类数据。此前要迁移它，用户得在「目录迁移」页点「＋」，
用文件选择器一路点进 `~/Pictures`，并且要知道 `.photoslibrary` 在 Finder 里表现为**一个文件**、在文件系统上却是
**一个目录**——直接点选会把选择器带进包内部，选中的是 `originals` 之类的子目录。就算选对了路径，还有三件事
没有任何提示会告诉用户：迁移期间照片 App 必须关闭、外置盘拔掉后照片会提示找不到图库、迁移完成后不需要
按住 Option 切换图库。

所以问题不是「缺一个搬运实现」，而是缺一个把这些前提说清楚、并且默认参数正确的入口。

## Decision

**只做入口，不做第二套搬运。** 卡片选择目标后创建的是一条普通的 `CustomDirConfig`，随后调用页面已有的
`submitDirectoryTasks` + `DataDirMover.migrateAndComplete`。这样图库迁移完成后，「接回 / 还原 / 断开链接」
在下面的本地文件夹列表里自动可用，`ManagedDataLinkRecord`、保留副本、清理重试这些机制也一并继承；
代价是它和其它自定义目录共享同一份配置存储，语义上确实就是「一条自定义目录配置」。

**发现与判定分离。** `PhotoLibraryDiscovery` 只负责在 `~/Pictures` 下找 `*.photoslibrary` 目录（同名普通文件排除），
`PhotoLibraryStateResolver.resolve` 只根据 `PhotoLibraryFacts`（本地是否存在、是否为软链、软链目标是否存在、
外置副本是否存在）给出状态。判定是这块唯一有分支的地方，抽成纯函数后可以完全不碰磁盘地覆盖
「实体目录 / 软链解析成功 / 软链悬空 / 本地缺失但副本还在 / 什么都没有」五种组合。

**照片 App 用 `terminate()` 并等待，绝不用 `forceTerminate`。** 图库正在写入时被强杀，比拒绝迁移糟糕得多。
`quitPhotos` 等 15 秒，仍不退出就如实报错，让用户自己关掉再点一次。

**目标盘先探能力再开搬。** 复用 `StorageCapabilityProbe`，要求目标支持 POSIX 权限位与资源叉。ExFAT/FAT
这类盘会把图库复制成「能看见、打不开」的样子，而失败现场是一整个几十 GB 的副本，事后清理成本很高，
因此在选择目标时就直接拒绝并说明原因。

**大小最后算。** 状态与按钮先出来，`measureDirectorySize(at:useCache:)` 放到 `Task.detached(priority: .utility)` 里，
按图库逐个更新。图库动辄几 GB，进页面就阻塞主线程做统计会让人以为界面卡死。

## Related decisions

- 与[迁移应用时一并迁移数据](2026-10-23-迁移应用时一并迁移数据.md)同源：都属于「把 `~` 下的用户数据搬到外置盘」，
  但那条通路针对 `.app` 的伴随目录（Application Support/Caches/WebKit/HTTPStorages），而图库是用户自己选中的独立目录，
  因此走自定义目录通路而不是 `AppCompanionDataMigration`。
- 与[容器卷改为挂载事件驱动](../bug-fix/2026-09-23-event-driven-container-remount.md)无关：图库不在 `~/Library/Containers` 下，
  不需要挂载迁移，软链不会被内核按解析后路径拒绝。
- 与[写入登记清理与挂载代理重启](../bug-fix/2026-10-23-写入登记清理与挂载代理重启.md)无关：图库不参与挂载代理的重挂循环。

## Alternatives considered

- **新增顶级 Tab「照片图库」**：发现性最好，但只为一类目录增加导航层级，会让「应用 / 工具目录 / 应用数据 / 目录迁移」
  这条主线被一个具体数据类型打断。放在「目录迁移」页顶部卡片既在最相关的位置，也不改导航结构。
- **让 Photos 直接记住外置图库路径（官方支持的「按住 Option 启动并设为系统照片图库」）**：不需要软链，
  但每一步都要 GUI 操作，App 无法代办，且未挂载时的表现与外置盘拔插的恢复路径都更依赖用户记忆。
- **迁移前强杀照片 App**：能保证一定搬得动，但图库可能停在写了一半的状态，风险与收益不成比例。
- **不检查目标盘格式，只给一条警告**：几十 GB 复制完才发现打不开，用户要自己判断「是哪一步错了」。
  探测成本只有几次 `openat`，没有理由省。
- **把图库大小直接算完再显示卡片**：会让进入「目录迁移」页慢上几秒到几十秒，且每次切换 Tab 都重复。

## Consequences

用户现在可以在「目录迁移」页顶部直接看到图库、大小与当前位置，点一次就能搬走；迁移后照片 App 行为不变，
因为本地路径始终存在（软链）。未发现图库时卡片只显示一行「未发现照片图库」，不占空间。

代价与约束：

- 图库是**系统照片图库**时，迁移后仍由 Photos 通过原路径访问。外置盘未挂载时 Photos 会提示找不到图库——
  这是软链模型的固有代价，界面已经写明「请连接后再打开照片」。
- 卡片只扫描 `~/Pictures`。图库被放在别处（例如已在另一块外置盘上）时不会出现在卡片里，但可以从
  「＋」按普通目录迁移接管，两条通路不冲突。
- 判定依赖 `PhotoLibraryFacts` 的五个布尔值；改动其中任何一个的采集方式（例如改用 `lstat` 判定软链）
  都要同时更新 `PhotoLibraryTests` 的构造用例。
- 目标盘能力探测失败（返回 nil）时**不**阻止迁移：探测不出来不等于有问题，这一点与 `StorageCapabilityProbe`
  在签名迁移里的处理保持一致。
