# Agent Note: 挂载类命令改由常驻特权助手执行，一次授权长期有效

Status: implemented

## Problem

「一次授权，永久有效」在 `do shell script … with administrator privileges` 这条通路上做不到：
AuthServices 的凭据挂在发起进程上，空闲约 5 分钟后失效，进程退出即消失。应用没有任何地方
可以保存它。结果是每次挂载容器卷都要再输一次密码，成批整理数据目录时会被连续打断。

同时，「要 root」的范围比实际需要的大：应用入口交换（`--privileged-app-transfer`）、
`chown -R` 修所有权、卷的创建与删除、以及挂载，全部走密码框。其中只有挂载是**反复发生**的。

## Decision

把 root 场景收缩到挂载一类，再用一次安装把这一次性成本摊平。

**范围收缩。** 删掉 `CodeSigner.ownershipRepairAppleScript`（唯一剩下的 `chown -R` 提权脚本，
只有一处测试引用它），需要修所有权时改为把应用挪回本地再操作。应用入口交换仍然只有
EACCES/EPERM 之后的一次性授权，**不**接常驻助手——它要求的是在 `/Applications` 里做
`RENAME_SWAP` 并清理原副本，能力比挂载大一个量级。`DiskUtility.run` 本来就是先试普通权限、
被 `kDAReturnNotPrivileged` 拒绝才提权，这条结构保留。

**常驻助手。** 四个文件分担四件事：

- `PrivilegedHelperProtocol.swift`：身份常量（`com.shimoko.AppPorts.privileged-helper`）、
  `@objc` XPC 协议，以及命令白名单 `PrivilegedMountCommand`。
- `PrivilegedHelperService.swift`：以 root 运行的 `NSXPCListener`（`dispatchMain()` 常驻），
  校验调用方、执行白名单命令。
- `PrivilegedHelperInstaller.swift`：把 plist 装进 `/Library/LaunchDaemons` 并 `bootstrap` 到
  system 域，整段是一个 `do shell script`，因此只弹一次密码。
- `PrivilegedHelperClient.swift`：应用侧客户端，握手 + 同步等待回复，最长 60 秒。

**白名单按「命令 + 词法形状」两层判定**：可执行文件只能是 `/usr/sbin/diskutil`、
`/sbin/mount`、`/sbin/umount`；`diskutil` 只放行 `mount`/`unmount`/`mountDisk`/`unmountDisk`/`info`；
`mount` 只接受带 `-u` 的原地重挂；`umount` 只接受一个绝对路径；每个参数必须是绝对路径或已知标志，
拒绝 `..`、`//`、控制字符和超长参数。助手用 `Process` 直接执行，不经过 shell，所以
`sh -c <脚本>` 这类命令**永远进不来**——`guardedCandidateMutationScript`、`apfs deleteVolume`
这些仍走一次性授权。

**调用方校验**（`PeerTrust`）：用 `SecCodeCopyGuestWithAttributes` 按 pid 取对端 `SecCode`，
先 `SecCodeCheckValidity` 确认签名有效——被改写过的副本在这一步就出局；再比对**签名身份指纹**
（`CodeIdentity`），而不是比对镜像哈希。指纹按强度分三级取值：有 Team ID 时只认
`identifier + Team`（重新编译、证书续期都不影响）；没有 Team 但有证书时认
`identifier + 叶子证书 SHA-256 前缀`；两者都没有（adhoc）才退回 cdhash。握手带回协议版本与同一份
指纹，客户端据此判断「是不是同一个发布者签的、接口是否兼容」。

之所以改成分级比较，是因为原先的「cdhash 必须与自身镜像完全一致」把两件不同的事混成了一件：
换了签名身份，和只是重新编译了一次，在 cdhash 看来完全一样。于是每次出包都要求用户重装助手、
再输一次密码——这正是这次要消掉的成本。分级之后，**有稳定证书的构建从此只需装一次**；只有
adhoc 构建仍然每次要重装，而那是签名本身的性质（adhoc 没有名字，只有内容哈希），不是代码能绕过的。

**安装位置**：只允许从 `/Applications` 安装。守护进程以 root 执行磁盘上的可执行文件，
若允许外置卷或用户可写目录，等于把 root 交给那个目录的写权限。

**回退**：任何一步不成立——没装、被拒、镜像过期、超时——`DiskUtility.runPrivileged` 都回到
原来会弹密码的通路。助手只是「少弹密码」的优化，不是唯一通路。

**日志**：助手不接 `AppLogger.shared`。那个单例会读 `UserDefaults`、按当前用户定位日志目录，
在 root 守护进程里既写不到用户能看的位置，也让特权进程多做一堆无关的事。助手的日志只写标准
错误，由 launchd 收进统一日志（`log show --predicate 'process == "AppPorts"'`）。这是对本仓库
「日志统一走 AppLogger」的唯一有意的例外。

## Related decisions

- 与[root 所有的应用只授权位置交换和已验证旧副本清理](../bug-fix/2026-10-20-root应用迁移授权.md)互为补充：
  那篇明确「不安装特权服务」，指的是应用入口交换；本篇只为挂载类命令引入常驻服务，应用交换仍是它
  定义的一次性受限入口，两篇的授权边界都不因此扩大。
- 与[容器卷改为挂载事件驱动](../bug-fix/2026-09-23-event-driven-container-remount.md)部分重叠：
  重挂的触发方式不变，只是执行时多数情况下不再弹密码框。
- 与[APFS 卷创建与所有权](../architecture/2026-10-01-apfs-owners-volume-creation.md)部分重叠：
  卷的创建、删除仍在白名单之外，继续走一次性授权。
- 与[写入登记清理与挂载代理重启](../bug-fix/2026-10-23-写入登记清理与挂载代理重启.md)无关：
  那篇改的是代理的触发方式与授权复用窗口，不改变谁能执行什么命令。

## Alternatives considered

- **延长 `do shell script` 的授权**：最省事，但 AuthServices 的凭据不可导出、不可写盘，
  `NSAppleScript` 复用已经是这条通路的极限（本次只把复用窗口从 120 秒对齐到系统的 300 秒空闲时限）。
  做不到「永久」。
- **`SMAppService` / `SMJobBless` 注册 helper**：这是 Apple 推荐的现代做法，但要求应用有稳定的
  Developer ID 签名与 Team ID；本机 `security find-identity` 为 0 个有效身份，连本地验证都跑不起来。
  另外它同样要弹一次批准，收益与手装 LaunchDaemon 相同，却把「能不能用」绑在签名上。
  最终采用手装 LaunchDaemon，同时把信任判定改成按签名身份分级——一旦补上证书，
  现有的手装通路就能自动获得「装一次长期有效」，不必推倒重来换注册机制。
- **信任判定继续只认 cdhash**：实现最简单，但等于把「换了证书」和「重新编译了一次」当成同一件事，
  每次出包都要重装助手。真正的约束不在校验方式，而在有没有稳定证书，所以选择把判定分级，
  让证书一旦就位就立刻生效。
- **按「路径 + 文件所有者」认客户端**（只在 `/Applications` 下、且所有者为 root 时就放行）：
  不依赖任何签名，adhoc 构建也能长期有效。但这样一来，任何能在该路径写入的进程都能指挥 root
  助手，把边界从「同一份签名」降级为「同一个目录权限」。否决。
- **setuid 辅助可执行文件**：省掉守护进程与 XPC，但任何能写该文件的用户都等于拿到 root，
  且 macOS 对 setuid 的约束（TCC、签名）会让它更难维护。否决。
- **把 `--privileged-app-transfer` 也接到助手**：调用点会少一次密码框，但等于让常驻 root 服务
  拥有「在 `/Applications` 任意交换目录名并递归删除」的能力，与白名单思路相反。否决。
- **助手接受任意 `diskutil` 子命令**：实现最短，但 `eraseVolume`、`deleteVolume` 一并获得 root，
  一次参数拼错就是数据丢失。否决。

## Consequences

装好之后，挂载与卸载容器卷不再弹密码；卷的创建、删除、签名修复和应用入口交换仍会弹，因为它们
不在白名单里。未安装时行为与改动前完全一致，因此这次改动不会让现有用户更差。

代价与约束：

- adhoc 构建下每次更新后 cdhash 变化，仍需重装一次助手；设置页会把状态显示为「需要重装」，
  握手会明确说明「与当前构建不匹配」。要免掉这一步，前提是给应用配一张稳定的证书
  （Team ID 最强，证书续期也不影响；本机自签证书也行，换证书时才需要重装），代码侧已经就位。
- 助手以 root 运行 `/Applications/AppPorts.app` 里的二进制。应用被移到外盘后无法再安装助手
  （安装器直接拒绝），已装的助手会因镜像不匹配而拒绝工作，两者都落到「弹密码」。
- daemon 的进程生命周期由 launchd 管理，`KeepAlive {SuccessfulExit: false}` 意味着助手崩溃会被拉起；
  正常退出不会。
- 白名单是安全边界，改动它等于改动攻击面，必须同时改 `PrivilegedMountCommandTests`。

## Verification

Xcode 装好后补做了真实构建与部署：

- `xcodebuild -configuration Release -destination 'platform=macOS' CODE_SIGN_STYLE=Manual
  CODE_SIGN_IDENTITY=-` **BUILD SUCCEEDED**（0 error）。首个版本报过一处编译错误，已修：
  `SecCodeCopySigningInformation` 只接受 `SecStaticCode`，`PrivilegedHelperService` 与
  `PrivilegedHelperClient` 都需要先 `SecCodeCopyStaticCode` 把运行中的 `SecCode` 落下磁盘镜像。
- 沙箱环境里插件服务器跑不起来（`sandbox-exec: sandbox_apply: Operation not permitted`），会让
  SwiftUI 宏报 `swift-plugin-server produced malformed response`；构建时附加
  `-disable-sandbox -plugin-path /Applications/Xcode.app/.../MacOSX.platform/Developer/usr/lib/swift/host/plugins`
  后从 1735 条错误降到 0。这是构建环境问题，与源码无关。
- 产物为 adhoc 签名（本机 `security find-identity` 仍为 0 个身份）、通用二进制，已替换
  `/Applications/AppPorts.app` 并正常启动（主进程 + `--mount-agent` 子进程都在）。
- 信任链用独立探针实测：对运行中的 AppPorts 取 `SecCodeCopyGuestWithAttributes` 返回 0，
  `SecCodeCheckValidity` 返回 0（adhoc 也能通过有效性校验），`kSecCodeInfoTeamIdentifier`
  为 nil，`SecCodeCopySigningInformation` 读到的 cdhash 与磁盘镜像 `CDHash` 完全一致。
  因此实际走的是 cdhash 分支：`anchor apple generic` 那条 requirement 在 adhoc 下返回
  `errSecCSReqFailed`，符合预期，代码也只有拿到 Team ID 时才会用它。
- 安装时序做了两处加固，都是「输完密码才发现失败」的典型坑：`bootout` 后轮询
  `launchctl print` 等旧实例消失再 `bootstrap`（异步退出的旧实例会让 `bootstrap` 报
  `Bootstrap failed: 5`）；安装后的握手改为最多 3 次重试，避免冷启动慢被误判成安装失败。
- 信任判定改成指纹分级后，协议版本从 `1` 升到 `2`：字段类型没变但含义变了，不升版本的话
  旧助手回一个 base64 cdhash，客户端只会报「身份不一致」，用户看到一串乱码而不是「需要重装」。
  `CodeIdentityTests` 用 9 条用例钉住三级优先级、`shortKind` 截断，以及
  **adhoc 重新构建后指纹必然变化**——最后这条是有意留下的「属性测试」，它把「adhoc 无法免重装」
  写成了可执行的断言，避免以后有人误以为改代码就能绕过去。
- 分级判定在真机上验证时发现一个不会报错的坑：`SecCodeCopySigningInformation` 用默认标志位
  取回的字典里**根本没有** `kSecCodeInfoCertificates`，必须带 `kSecCSSigningInformation`。
  少了这个标志，证书层永远不命中，指纹永远落回 cdhash——症状与「没配置证书」完全一样，
  只有把两种签名放在一起对比才看得出。已修，并把 `snapshot(of:)` 拆出来让磁盘镜像也能取快照，
  新增用例拿 `/bin/cp` 当基准（系统二进制一定带证书）钉住这个标志位。
- 自签证书链路实测（临时证书签一份副本）：`SecStaticCodeCheckValidity` 返回 0，说明
  nil requirement 的有效性校验不要求 Apple 锚定，自签证书同样能通过第一道闸；签名信息里
  `certificates` 有 1 张，指纹为 `cert|com.shimoko.AppPorts|<16字节十六进制>`。
  同一份源码的两次签名（一次重签副本、一次完整构建）cdhash 分别是
  `myBMDjaRMEjBb5JezKPCbuzNe/Q=` 与 `xXY36Wp6SEUkODDRi0MC65WwljM=`，**指纹完全一致**——
  「重新构建不必重装助手」由此从推断变成实测。
- 顺带修掉一个既有的本地化缺陷：原「特权助手运行的仍是旧镜像（…）」是用字符串插值拼出来的，
  因此从来不在 catalog 里，非中文用户永远看到中文。改成 `String(format:)` 的单键后，
  本次新增的 8 个键按 `LocalizationAuditTests` 的五条规则逐条核对（22 个语种齐备、
  占位符一致、拉丁语系无汉字、非中文未复用中文键、未与英文相同）：**0 问题**；
  catalog 以 `separators=(',', ' : ')` 重排后与磁盘字节完全一致，无意外格式漂移。
- `PrivilegedMountCommandTests` 与 `swiftc -typecheck` 覆盖见上文；测试套件仍未在本机运行。

尚未验证、必须补的（都需要在主会话里点一次系统授权框，代理跑不了）：真实安装与握手
（弹一次密码后挂载不再弹）、应用更新后「需要重装」的提示、助手拒绝外来调用
（另起一个未签名副本尝试连接）、以及白名单之外命令的回退是否仍然弹密码。
